1. OBJETIVO Y DECISIONES

Construir un motor común reutilizable y aplicaciones de negocio independientes que se conecten exclusivamente mediante una API. El sitio público, el panel compartido de negocios y el panel de plataforma tendrán responsabilidades, permisos y ciclos de desarrollo diferenciados. Un sitio podrá cambiarse o sustituirse sin modificar el núcleo; cada negocio mantiene sus propios datos y configuración.

Decisiones orientativas adoptadas con el usuario:
- SQLite para desarrollo y pruebas hasta disponer de un prototipo sólido y verificable. La elección para uso real se evaluará después según concurrencia, operación y evidencias; no presupone una migración.
- Un panel compartido de negocio, con acceso y datos aislados por negocio; habilitar solo los módulos que correspondan. Un panel específico de un cliente es posible posteriormente por API, sin adaptar el núcleo a ese cliente.
- Funciones de administración general de plataforma separadas lógica y operativamente, con autorización reforzada; pueden compartir componentes de interfaz cuando resulte apropiado. No asumir que los administradores tienen acceso indiscriminado a datos de clientes.
- Fripollo es una marca y carta ficticias, usadas solo para demostración hasta que el cliente confirme información real. La web de ejemplo es una aplicación independiente; no se integran su marca, textos, carta ni reglas particulares en el dominio común.
- Las fases no comprometen fechas ni presupuesto. Las decisiones técnicas de infraestructura, seguridad y contratos se validarán al implementarlas.

3. ORGANIZACIÓN PROPUESTA Y LÍMITES

[PROPUESTO] Componentes lógicos:
  A. Núcleo de dominio y aplicación: conceptos y casos de uso generales.
  B. Servicio API: adaptador HTTP, identidad, autorización, validación y composición de infraestructura.
  C. Panel de negocios: aplicación React compartida, configurable por negocio y funciones autorizadas.
  D. Panel de plataforma: interfaz y permisos diferenciados para administración global.
  E. Sitios de negocio: proyectos o aplicaciones independientes (Fripollo, futuros clientes), con identidad visual y configuración propias.
  F. Infraestructura: repositorios, SQLite en el prototipo, migraciones y procesamiento de eventos.

La separación lógica es obligatoria; decidir monorepositorio con paquetes aislados frente a repositorios separados durante la fase 1. Cada cliente consume contratos públicos versionados; ningún frontend accede a SQLite directamente ni importa repositorios o tablas internas. La configuración pública de un sitio no contiene secretos. Ubicación/tenant/negocio del servidor se deriva o valida desde identidad y autorizaciones; ningún identificador enviado por el navegador concede acceso por sí solo.
